# QA 独立图片异步存储方案

作者：hyp  
日期：2026-10-28  

状态：短图片 ID 版本已构建为 ragflow:0.26.4-qa-images-short-id，待用户验证，未切换现有服务；此前目录格式已完成本地 MinIO 联调，实际 OSS 尚未联调

## 1. 目标与范围

当前使用 RAGFlow 0.26.4，数据库为 MySQL，图片存储使用现有 OSS。

Word、PDF 使用 QA 解析时，一个问答对关联的图片最终成为一张合并图。为后续向用户依次返回独立图片，本次增加独立图片存储和映射，不改变一个问答对对应一个切片的规则。

本次仅处理首次上传、解析后的图片存储：

- 保留合并前的独立图片或识别出的独立插图区域。
- 异步上传到现有 OSS。
- 将合并图、切片和有序 OSS 路径列表的关系保存到 MySQL。

存储阶段不处理重新解析、历史数据补齐、文档删除联动和前端展示。后续新增召回接口的范围及行为见第 12 节，原有召回接口保持不变。

## 2. 已确认的源码行为

| 位置 | 当前行为 |
| --- | --- |
| `rag/app/qa.py` 中的 `Docx` | 调用 `get_picture()` 获取段落图片，通过 `concat_img()` 累积到当前问答 |
| `deepdoc/parser/docx_parser.py` 中的 `get_picture()` | 将段落中的图片二进制保存在 `LazyImage` 中 |
| `rag/utils/lazy_image.py` | `to_pil()` 将累积的图片转换并合并为一张图 |
| `rag/app/qa.py` 中的 `Pdf` | 使用当前问答的区域标记调用 `crop()` |
| `deepdoc/parser/pdf_parser.py` 中的 `crop()` | 裁切问答相关区域并拼接，可能包含文字、插图和表格 |
| `rag/svr/task_executor.py` | 生成切片 ID，调用图片存储逻辑 |
| `rag/utils/base64_image.py` 中的 `image2id()` | 上传单张图片并设置 `img_id` |
| `api/db/db_models.py` | 已有 `ListField`，业务层读写 List，底层序列化为文本 |

Word 与 PDF 必须分别处理。PDF 的问答截图不能直接当成独立图片列表，需要保留已经识别并归属于问答的插图区域。扫描件能拆出多少插图取决于版面识别结果，不承诺还原 PDF 内部的原始图片文件。

## 3. 整体流程

```text
用户上传 Word / PDF
        ↓
QA 解析
        ├─ 原有数据：问答内容、合并图
        └─ 新增数据：按原文顺序保留的独立图片
        ↓
原有流程：合并图上传 OSS → 切片入库成功
        ↓
提交独立图片后台任务，原有解析正常完成
        ↓
后台任务：独立图片上传 OSS → 整理路径 List → 写映射表
```

例如一个问答对包含三张图片：

```text
原有：切片 C001 → 合并图 M001
新增：C001 + M001 → [图片1 OSS 路径, 图片2 OSS 路径, 图片3 OSS 路径]
```

## 4. MySQL 表设计

表名建议为 `chunk_image_mapping`，一条记录保存一个切片对应的整组图片。

| 字段 | MySQL 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGINT AUTO_INCREMENT` | 主键 |
| `kb_id` | `VARCHAR(32)` | 知识库 ID |
| `doc_id` | `VARCHAR(32)` | 文档 ID |
| `chunk_id` | `VARCHAR(64)` | 切片 ID |
| `merged_image_id` | `VARCHAR(128)` | 原有合并图完整存储标识 |
| `image_paths` | `LONGTEXT` | 有序 OSS 路径 List，复用项目 `ListField` |
| 公共时间字段 | 沿用项目公共模型 | 创建、更新时间 |

约束与索引：

- `(kb_id, doc_id, chunk_id)` 建立唯一索引，后台任务重试不能重复新增记录。
- `(kb_id, merged_image_id)` 建立查询索引，方便后续通过合并图查找独立图片。
- 唯一索引的前提是一个切片维护一组图片；实施前必须核实同文档重复问答的实际切片去重行为。

`image_paths` 在业务代码中就是有序 List，不拆成多行，也不增加排序字段。MySQL 没有原生 List 列类型；现有 `ListField` 将 List 编码为 JSON 文本存入 `LONGTEXT`，读取时自动还原。这是存储编码，表中的其他字段仍独立定义。

数据库只保存 OSS 稳定路径或现有完整对象标识，不保存图片二进制、Base64、临时签名 URL、OSS 访问密钥。具体路径格式沿用现有 OSS 适配器，不能只存无法区分 bucket 的对象名。

## 5. 图片提取和 OSS 存储

### Word

在 QA 路径保留合并前的独立图片，包括同一段落中的多张图片。按原文出现顺序组织，保留重复出现，不做集合去重。

原有 `LazyImage` 和合并图处理继续执行。旁路不得修改原有图片对象、提前关闭其资源或消耗原流程仍需使用的数据。

### PDF

沿用现有问答归属判断，保留归属于当前问答的独立插图区域，不从最终合并长图反向猜测边界。不修改公共 `crop()` 的行为。

本方案默认保存插图；表格是否作为图片保存仍需明确。无可识别独立图片的问答不创建映射记录。

### OSS 路径

独立图片与原有合并图统一使用无目录、无扩展名的 16 位十六进制对象名。每张图片根据知识库、文档、切片、图片组摘要及序号计算稳定短 ID，并使用独立命名域区分合并图。示意：

```text
存储对象名：a7c42e9160bf38d2
数据库 image_paths：["知识库ID-a7c42e9160bf38d2", "知识库ID-f1938b62c0da745e"]
```

图片内容仍为 JPEG，与原合并图一致，不要求对象名带 `.jpg` 后缀。数据库字段和新接口字段仍叫 `image_paths`，但元素为单图 ID，不是目录路径或签名 URL。上传、重试校验和失败清理统一使用短对象名；List 按原文顺序排列。同一任务重试复用对象名，原合并图 ID 和原接口保持不变。

此次调整仅作用于采用新代码处理的独立图片，历史目录格式记录和对象不迁移、不删除。历史任务和记录仍需保留原版本处理，不应在有旧版本待处理图片任务时切换命名规则。短 ID 版本采用独立镜像标签 `ragflow:0.26.4-qa-images-short-id`，镜像内 21 项针对性测试通过；没有重启现有服务或修改工具项目。

## 6. 异步处理与失败隔离

独立图片上传和关系表写入由后台任务处理，原有解析不等待其完成。不能仅启动一个无跟踪的 `asyncio.create_task()` 就认为任务可靠完成。

后台任务需要拿到真实图片数据。解析产生的内存对象不能在解析结束后直接丢弃，也不能把尚未上传的目标 OSS 路径当作已有数据。

实施时优先检查并复用现有队列与暂存机制：

1. 暂存独立图片，形成可由后台消费者读取的任务输入。
2. 原有切片入库成功后，尽力提交独立任务。
3. 后台消费者读取暂存图片并上传 OSS。
4. 全部上传成功后，事务写入完整映射。
5. 成功后清理暂存数据；失败采用有限次数重试，重试耗尽后记录明确错误。

当前实现复用现有 Redis：图片二进制编码后暂存在独立缓存键中，有效期为 24 小时，单个切片暂存内容上限为 16 MiB。独立 Stream 使用 `ragflow:qa-images`，消息只放关联 ID 和缓存位置，不放图片二进制。消费者在原执行器进程内独立运行，不占用原解析任务并发额度。重启后按相同消费者名称恢复自己的未确认任务，不承诺在消费者名称变化后自动接管旧任务。

旁路提取、暂存、任务提交、上传和写表的异常均不得向原有解析链路传播，也不得改变原有成功状态。原有流程自身的异常处理保持原样。

额外处理仍会消耗 CPU、内存、磁盘、带宽和存储，不能承诺零性能影响。应限制并发、待处理任务数量和暂存占用；新增处理达到容量上限时跳过本次旁路并记录错误，优先保障原有解析。

## 7. 不修改的部分

- 原有切片 ID、合并图 ID 和合并图 OSS 路径。
- 公共 `concat_img()`、`crop()` 的行为。
- 原有检索索引字段、对外返回结构和前端。
- 原有任务成功、失败的判定规则。

新增处理限定在 QA 路径，自动执行独立图片的异步存储。

## 8. 必须明确的限制

- 原有解析完成时，独立图片映射可能尚未就绪，这是异步处理的正常结果。
- OSS 与 MySQL 没有共同事务；上传成功但写表失败时可能产生孤立对象。依靠稳定对象名重试，并清理本次未被映射引用的对象；不能删除原有合并图。
- 当前切片 ID 根据文本内容与文档 ID 计算，图片内容不参与。相同文字、不同图片可能具有相同切片 ID。本次不改 ID 算法，实施前必须验证重复问答场景；存在冲突时不能静默覆盖关系，也不能宣称覆盖该场景。
- 重新解析与删除联动尚未实现，本方案不能作为这些场景的数据一致性保证。

## 9. 验收标准

1. Word 问答中有三张图片，原有切片和合并图正常生成，后台生成三个有效 OSS 路径，顺序与原文一致。
2. 同一 Word 段落有多张图片时，每张均独立保存。
3. PDF 问答有多个可识别插图时，分别保存，不能把纯文字区域作为插图返回。
4. 无图片的问答不新增关系记录。
5. 后台任务失败、队列不可用、OSS 上传失败或数据库写入失败时，原有解析结果不受影响。
6. 任务重试不重复新增映射，不覆盖原有合并图。

## 12. 带独立图片的新增召回接口

新增 `POST /api/v1/retrieval/images`，原有 `POST /api/v1/retrieval` 不变。

新入口直接调用原入口（包括原入口的鉴权装饰器），因此请求参数、知识库权限校验、过滤、重排、分页、图谱召回、目录增强和元数据能力沿用原接口。原接口返回错误时，新入口原样返回错误，不执行图片查询。

仅对成功响应进行 JSON 解码并补充图片，不修改检索器内部可能共享的结果对象。保留原有 `image_id`、聚合结果、状态码及响应头，在每个切片中增加 `image_paths`。该字段沿用映射表中的有序内部存储标识，不在此接口生成签名或改变原有图片存储格式。

请求示例（请求参数及认证信息与原召回接口一致）：

```bash
curl -X POST 'http://服务器地址/api/v1/retrieval/images' \
  -H "Authorization: Bearer $RAGFLOW_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"dataset_ids":["知识库ID"],"question":"问题","page":1,"page_size":10}'
```

切片返回示例（其余原有字段保持原样）：

```json
{
  "id": "原切片ID",
  "dataset_id": "知识库ID",
  "document_id": "文档ID",
  "image_id": "原合并图ID",
  "image_paths": ["第一张图片的内部存储标识", "第二张图片的内部存储标识"]
}
```

图片查询按本次已鉴权召回结果中的知识库、文档和合并图标识批量执行，不能仅通过合并图标识跨知识库取图。

以下均是正常结果，返回 `image_paths: []`，不报错、不记录错误日志：

- 切片没有合并图标识。
- 合并图没有对应映射，包括旧文档和异步任务尚未完成的情况。
- 映射中的图片列表为空。

只有映射数据库查询本身异常时才记录错误日志；新接口仍保留原召回结果，图片列表为空。不额外请求 OSS 检查对象是否存在，因此不会因 OSS 暂时不可用而改变召回能力。

新增入口会批量读取 MySQL 映射，原召回入口不会触发这次新增查询。测试服务器需重新导入包含此接口的新镜像并重建应用容器，旧镜像不会自动获得新路由。

验证结果：新增召回扩展测试 10 项与原图片存储测试 10 项在更新后的镜像中全部通过；新增文件的 Ruff 检查和 80 列格式检查通过。本地实际 HTTP 检查确认原、新接口对未登录请求均返回相同的 HTTP 401 和相同响应内容。成功召回的参数传递、原字段保留、批量映射及缺失图片处理通过隔离测试验证，尚未在测试服务器完成带真实嵌入模型的成功召回联调。
